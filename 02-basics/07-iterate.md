# 답변을 계속 수정시키기

> 상태: 초안

## 이번 장에서 할 일

첫 결과를 평가하고, **한 번에 분명한 변화 하나씩 요청해 실제 산출물로 완성**합니다.

## 프롬프트 작성보다 중요한 능력

첫 요청이 아무리 자세해도 결과가 한 번에 완벽하지 않을 수 있습니다. 빠진 정보를 발견하거나, 읽어보니 목적이 바뀌거나, 예상하지 못한 좋은 방향을 찾기도 합니다.

그래서 ChatGPT 활용은 다음의 반복 과정입니다.

```text
요청 → 결과 확인 → 문제 진단 → 수정 요청 → 검증 → 사용
```

새 대화를 시작할 필요 없이 같은 대화에서 이어서 말할 수 있습니다.

## “다시 해줘”보다 구체적으로 말하기

```text
다시 써줘.
```

이 요청만으로는 무엇을 고쳐야 하는지 알기 어렵습니다. 다음 세 가지 중 필요한 것을 말합니다.

1. **유지할 것:** 지금 결과에서 좋은 부분
2. **바꿀 것:** 문제와 원하는 변화
3. **확인할 것:** 수정 뒤 검증해야 할 조건

```text
회의 정보가 글머리표로 정리된 구조는 유지해줘.
첫 문장이 너무 딱딱하니 외부 고객에게 자연스럽고 정중하게 들리도록 바꿔줘.
수정한 뒤 날짜와 회신 기한이 그대로인지 확인해줘.
```

## 결과를 진단하는 다섯 질문

수정 요청을 보내기 전에 다음을 확인합니다.

1. 목적을 이루는가?
2. 독자에게 맞는가?
3. 중요한 내용이 빠지지 않았는가?
4. 틀리거나 추측한 내용은 없는가?
5. 실제 사용할 형태인가?

문제의 이름을 붙일 수 있으면 수정 요청도 쉬워집니다.

| 문제 | 수정 요청 예시 |
|---|---|
| 너무 길다 | 핵심 정보는 유지하고 본문을 7문장 이내로 줄여줘. |
| 말투가 딱딱하다 | 외부 고객에게 정중하지만 자연스러운 말투로 바꿔줘. |
| 결론이 늦다 | 회의 목적과 요청사항을 첫 두 문장에 배치해줘. |
| 내용이 빠졌다 | 준비할 자료와 회신 기한을 추가해줘. |
| 사실을 지어냈다 | 제공하지 않은 장소와 링크를 삭제하고 “확인 필요”로 표시해줘. |
| 선택지가 필요하다 | 첫 문장만 서로 다른 방향으로 3개 제안해줘. |

## 한 번에 하나의 큰 문제를 고치기

여러 문제를 한꺼번에 바꾸면 무엇이 좋아졌는지 판단하기 어렵습니다. 중요한 문제부터 고칩니다.

```text
1차 수정: 빠진 회신 기한을 추가해줘.
```

```text
2차 수정: 내용은 그대로 두고 문장을 더 짧게 만들어줘.
```

```text
3차 수정: 날짜, 시간, 회신 기한이 원래 정보와 같은지 확인해줘.
```

관련된 작은 변경은 함께 요청해도 괜찮습니다. 핵심은 변경 결과를 내가 확인할 수 있어야 한다는 것입니다.

## 방향이 틀렸을 때 되돌리기

수정 결과가 더 나빠졌다면 좋은 부분으로 돌아갈 수 있습니다.

```text
방금 버전보다 이전 버전의 구조가 더 좋아.
이전 구조로 돌아가되 회신 기한만 추가해줘.
```

```text
내 요청을 잘못 설명했어. 회의 취소가 아니라 날짜 변경 안내야.
취소로 이해한 내용은 모두 빼고 다시 작성해줘.
```

ChatGPT의 방향을 고치는 것은 사용 실패가 아니라 정상적인 협업 과정입니다.

## 큰 작업은 중간 결과를 확인하기

긴 보고서나 발표자료처럼 큰 결과는 마지막까지 기다리기보다 중간 단계에서 방향을 확인합니다.

```text
아직 본문을 쓰지 말고 먼저 목차와 각 절의 핵심 메시지만 제안해줘.
```

```text
이 구조에서 빠진 내용과 겹치는 내용을 찾아줘.
내가 승인한 뒤 본문을 작성해줘.
```

중간 승인을 두면 잘못된 방향으로 많은 내용을 만드는 일을 줄일 수 있습니다.

## 회의 안내 이메일 완성 과정

### 1. 시작

```text
회의 안내 이메일을 작성해줘.
```

### 2. 결과와 독자 설명

```text
외부 고객에게 보내는 프로젝트 중간 점검 회의 안내야.
변경 일정을 확정하고 참석 가능 여부를 회신받는 것이 목적이야.
```

### 3. 맥락과 사실 추가

```text
지난 회의에서 일정 지연 가능성을 이미 공유했어.
회의는 10월 15일 오후 2시이고, 장소와 링크는 아직 정해지지 않았어.
```

### 4. 조건과 형식 추가

```text
제목, 인사말, 회의 목적, 회의 정보 글머리표, 회신 요청의 순서로 작성해줘.
본문은 7문장 이내로 하고, 10월 10일까지 회신을 요청해줘.
정해지지 않은 정보는 추측하지 마.
```

### 5. 말투 조정

```text
구조와 사실은 유지해줘.
지연을 변명하는 느낌 없이, 해결을 위해 함께 일하는 정중한 말투로 바꿔줘.
```

### 6. 최종 검증

```text
보내기 전 다음을 확인해줘.
- 날짜, 시간, 회신 기한이 내가 준 정보와 같은가?
- 장소와 링크를 지어내지 않았는가?
- 고객이 무엇을 해야 하는지 분명한가?
- 7문장 이내인가?
문제가 있으면 먼저 수정하고, 확인 결과를 짧게 알려줘.
```

마지막으로 사용자가 실제 날짜, 수신자, 표현을 직접 확인한 뒤 발송합니다.

## 요청을 한 번에 합쳐야 할 때

같은 업무를 반복하게 되면 앞에서 발견한 조건을 하나의 재사용 가능한 요청으로 합칠 수 있습니다.

```text
외부 고객에게 보낼 프로젝트 중간 점검 회의 안내 이메일을 작성해줘.

[목적]
변경 일정을 확정하고 참석 가능 여부를 회신받기

[맥락]
지난 회의에서 일정 지연 가능성을 이미 공유함
고객은 기술 용어에 익숙하지 않음

[이번 회의 정보]
- 일시: 10월 15일 오후 2시
- 장소와 링크: 아직 미정
- 회신 기한: 10월 10일

[결과 형태]
제목, 인사말, 목적, 회의 정보 글머리표, 회신 요청

[조건]
- 본문 7문장 이내
- 짧고 정중하며 해결 지향적인 말투
- 제공하지 않은 정보는 추측하지 않고 “확인 필요”로 표시

[완료 전 확인]
날짜, 시간, 회신 기한과 미정 항목을 다시 확인해줘.
초안만 작성하고 실제로 발송하지 마.
```

이 형식은 의무가 아닙니다. 반복 사용하기 편하도록 정리한 템플릿일 뿐입니다.

## 수정이 끝나는 기준 정하기

“더 좋게”를 계속 반복하면 끝이 없습니다. 시작하기 전에 완료 기준을 정하세요.

- 목적과 독자가 분명하다.
- 필수 정보가 모두 있다.
- 확인되지 않은 사실이 없다.
- 실제 사용할 형식이다.
- 담당자가 최종 검토했다.

기준을 충족하면 더 다듬기보다 실제 업무에 사용하고, 다음번에 개선할 점을 기록합니다.

### 완료 체크

- [ ] 결과의 가장 큰 문제를 먼저 찾았다.
- [ ] 유지할 것과 바꿀 것을 구분해 요청했다.
- [ ] 한 번 이상 후속 요청으로 개선했다.

## PART 2 최종 점검

- [ ] 짧은 요청으로 시작할 수 있다.
- [ ] 원하는 결과와 독자를 설명할 수 있다.
- [ ] 결과를 바꾸는 맥락을 고를 수 있다.
- [ ] 중요한 조건과 경계를 정할 수 있다.
- [ ] 실제 사용처에 맞는 결과 형태를 고를 수 있다.
- [ ] 예시에서 따라 할 특징을 설명할 수 있다.
- [ ] 후속 대화로 결과를 수정하고 검증할 수 있다.
